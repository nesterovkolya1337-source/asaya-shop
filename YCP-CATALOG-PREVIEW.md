# YCP: проверка корзины и склады

> Следующий этап реализован: создание, подтверждение и отмена сессии — [YCP-CHECKOUT-PREVIEW.md](YCP-CHECKOUT-PREVIEW.md). Для текущей версии уже нужна миграция 013; указание 001–012 ниже относится к этапу первых двух методов.

## Согласованный сценарий

Владелец подтвердил 06.09.2026: оформление и оплата идут через Яндекс. Отдельные Robokassa/CloudPayments не подключаем. Дальнейшая работа строится вокруг YCP, включая согласование доставки через настройки Яндекса. Старый план отдельных интеграций СДЭК не считается подтверждением необходимости писать отдельный адаптер.

Контракт сверён с официальной [OpenAPI YCP 0.0.14](https://yandex.ru/support/merchants-ru-ycp/ru/openapi/) 06.09.2026. SHA-256 извлечённого JSON: `7a66234bdfc62cdceff36019f84be7374a2ab69ec652b7ebe05b87600c1c2ec0`. Полная сторонняя спецификация в архив дополнения не включена.

## Реализовано

Базовый путь адаптера — `/api/ycp/v1`. На backend доступны:

- `GET /warehouses?limit=1000&offset=0`: настроенные активные склады, полные адреса и телефоны, стабильный порядок, пагинация и общее количество. Самовывоз отключён до отдельной настройки его расписания.
- `POST /checkout/basket/check`: актуальные цены, доступный остаток по складам после вычитания резерва, размеры в миллиметрах и вес в граммах, ссылки на карточки и опубликованные изображения при наличии. Характеристики и варианты пока пустые, что допускается контрактом.

Оба метода проверяют отдельный Bearer-токен до разбора тела. Пользовательские cookie не нужны и не заменяют токен. Исключение из проверки Origin действует только для этих двух зарегистрированных методов; защита пользовательского и административного API сохраняется. При отсутствии конфигурации методы возвращают 503. Ответы не кэшируются; токен исключён из логов.

При `offers_id_from_merchant_center=true` идентификатор ищется только в `product_external_ids` с provider=`ycp`, выбранным account_id и environment=`test`. Автоматического предположения, что offerID совпадает с SKU или slug, нет. При false принимается SKU. Для наполнения соответствий нужны реальные offerID из фида кабинета Яндекса и внутренние product_id.

Корзина проверяется одним запросом БД. Скрытые товары, неутверждённые цены, неутверждённые связи витрины и наборы с компонентным учётом не выдаются. Если запрошенный товар не найден или недоступен для продажи, возвращается 404 для всей проверки. Нулевой остаток передаётся как 0. Неизвестный регион получает пустой список складских остатков. Проверка не резервирует товар и не создаёт заказ, в том числе при `is_health_check=true`.

## Настройка

Скопируйте `backend/data/ycp-settings.example.json` в отдельный приватный файл вне репозитория. В окружении backend задайте вместе `YCP_TOKEN` (отдельный случайный токен не короче 32 символов) и `YCP_SETTINGS_FILE` (путь к файлу). Токен передаётся в кабинете YCP отдельно; его нельзя добавлять в клиентский код. Новых миграций нет: используются 001–012.

В settings задаются accountId, публичный HTTPS-адрес магазина, денежная единица, НДС и профили существующих складов. Профиль склада:

```json
{
  "warehouseId": "UUID существующего склада из БД",
  "address": "Подтверждённый полный адрес склада",
  "phone": "Подтверждённый телефон склада",
  "servedLocalities": ["Москва"],
  "ycpDeliveryEnabled": false
}
```

`servedLocalities` задаёт разрешённые регионы явно; `*` разрешает все регионы только при сознательном указании. Регистр и пробелы по краям названий не учитываются. `ycpDeliveryEnabled` соответствует `ycp_delivery_options.enabled` контракта; это не флаг наличия прямого подключения СДЭК. Фактический режим выбирается вместе с настройками логистики кабинета Яндекса.

В опубликованной OpenAPI цена обозначена integer без указания рублей/копеек. Поэтому `priceUnit=null` блокирует ответ корзины до сверки единицы с Яндексом. Для подтверждённых копеек используется `minor`, для целых рублей — `rubles`; в режиме rubles дробная цена отклоняется, а не округляется. `vat=null` также блокирует ответ: ставку магазина не угадываем. Эти настройки не означают, что выбор единицы или ставки уже подтверждён. Отсутствие веса/габаритов возвращает 503, чтобы не передавать выдуманные параметры доставки.

## Границы этапа

Проверки: компиляция backend прошла; 67 существующих тестов прошли при полном запуске. После исправления типов в фикстуре новых тестовых складов отдельно прошли все 6 тестов YCP. Итого подтверждены 73 теста без пропусков. Проверены реальные HTTP-маршруты через Fastify inject и временный PostgreSQL, но не сетевой вызов из Яндекса. Витрина не менялась; её сборки повторно не запускались.

Адаптер пока разрешает только тестовую среду. Он проверяется локально через HTTP-запросы и временный PostgreSQL; подключение к реальному кабинету Яндекса, внешний HTTPS-маршрут и приёмка Яндексом ещё не выполнены. Исходный сайт и production не менялись.

Следующие обязательные части: `/checkout` с повторной проверкой и резервом; `/checkout/placed` и `/checkout/cancel` с устойчивой обработкой повторов; `/order/delivered`, `/order/cancel` и `/order`; передача offerID/каталога и кнопка Яндекса на витрине. Необходимость методов расчёта доставки определяется выбранным режимом в Яндексе. До этих частей полный цикл YCP не готов.
