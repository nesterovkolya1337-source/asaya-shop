# Фоновое освобождение просроченных резервов

Добавлен отдельный процесс бэкэнда, который автоматически вызывает существующую транзакционную обработку просроченного оформления. По умолчанию первая проверка начинается сразу, следующие — через 60 секунд после окончания предыдущей. Один проход обрабатывает не более 100 кандидатов; оставшиеся попадут в следующие проходы.

Отменяются только заказы со статусом `draft`, оплатой `pending`/`failed`, открытой сессией и истёкшим сроком. Статус перепроверяется под блокировкой заказа. Резерв снимается, отмена записывается в историю и журнал, событие сохраняется в очередь. Успешно оплаченные, оформленные через Яндекс и отправленные заказы не подпадают под этот отбор. Позднее подтверждение Яндекса обрабатывается существующим сценарием проверки, без восстановления снятого резерва.

Процесс ждёт завершения каждой проверки, не создаёт параллельных таймеров и повторяет попытку после временной ошибки базы. В журнал выводятся только тип события и количество обработанных заказов. Текст исключений и данные подключения не записываются. SIGINT/SIGTERM прерывают ожидание, дают текущей проверке завершиться, затем закрывают соединения с базой.

## Запуск в тестовой среде

Из каталога backend после `npm run build`, с настроенной переменной DATABASE_URL:

```sh
# Одна проверка (не более 100 заказов)
npm run reservations:expire -- --once

# Постоянный процесс
npm run reservations:expire -- --watch
```

`RESERVATION_SWEEP_INTERVAL_MS` задаёт интервал в миллисекундах: по умолчанию 60000, допустимо 1000–300000. Некорректные параметры отклоняются до подключения к базе. Для локального .env можно запускать `node --env-file=.env dist/scripts/expire-reservations.js --watch`.

Процесс запускается отдельно от HTTP-сервера. Системная служба, автозагрузка Windows/Linux и production-развёртывание этим этапом не устанавливались. Режим NODE_ENV=production заблокирован, как и текущая YCP-интеграция. На рабочей базе пользователя команда не запускалась. Реальные остатки, товары и заказы не изменялись.
