# Backend ASAYA первый этап

Самостоятельный backend для локальной проверки. Основа: Fastify, TypeScript, PostgreSQL. Витрина, исходный read-only проект, GitHub и production не подключались к новым операциям.

## Реализовано

- Семь SQL-миграций с контрольными суммами и блокировкой одновременного запуска.
- Импорт XLSX через промежуточный JSON: все строки сохраняются в реестре, продукция становится черновиками, комплектующие/услуги/маркетплейсы не попадают в каталог продаж.
- Стабильные SKU, отдельные штрихкоды, исходные идентификаторы, 17 кандидатных связей карточек. Ни одна связь и ни один товар не включаются в продажи автоматически.
- Серверный расчёт заказа в целых копейках; снимки позиций, контактов, доставки и согласий. Цены и стоимость доставки из браузера не принимаются.
- Атомарные резервы на конкретном складе, защита от перепродажи последнего остатка, отмена и истечение срока.
- Идемпотентность по пользователю и ключу запроса; отличающийся запрос с тем же ключом отклоняется.
- Внутренняя обработка подтверждённой оплаты, проверка суммы/окружения/идентификаторов; повторные события не создают новые платежи. Поздняя оплата отменённого заказа сохраняется для разбора.
- Inbox/outbox с повторными попытками, сроком аренды задачи и стабильным ключом внешней операции.
- OTP по email/SMS через интерфейс OtpSender, HMAC кодов, срок 5 минут, 5 попыток, повтор через 60 секунд, лимиты по получателю и IP в БД.
- Серверные сессии, HttpOnly cookie, проверка Origin и CSRF, отзыв сессии и запрет доступа к чужому заказу.
- Клиентский OTP не выдаёт доступ сотрудникам; администраторские операции требуют будущей отдельной авторизации с вторым фактором.

## Границы этапа

Это foundation, а не подключённый магазин. `server.ts` намеренно запрещает `NODE_ENV=production`.

В production-контракт ещё не включены полный цикл YCP, реальные оплаты/возвраты через Яндекс, согласованный режим логистики, внешний OTP-провайдер и реальные согласия. Каталог, вход и админка сайта работают локально. Первые методы YCP описаны в `../YCP-CATALOG-PREVIEW.md`. Полный жизненный цикл возвратов пока не реализован.

Обычный запуск использует DisabledOtpSender и возвращает 503 на отправку OTP. Он не выдаёт фиктивный код. Для тестов используется MemorySender только внутри test-файла. Для подключения поставщика надо реализовать `sendOtp` и передать адаптер в `buildApp`; публичные маршруты не меняются.

Delivery quote создаётся через DeliveryService и интерфейс DeliveryProvider. По умолчанию поставщик отключён: 503 без фиктивного тарифа. Корзина, расчёт, checkout и восстановление попыток подключены к локальной витрине отдельным тестовым флагом; запуск изолированного стенда — в ../CHECKOUT-PREVIEW.md. Публичный checkout не может назначить себе бесплатную доставку.

Входящий YCP-заказ получает отдельную гостевую запись без возможности входа. Контакты сохраняются в заказе, но не становятся подтверждёнными user_identities и не привязывают заказ к местному аккаунту по email. Внутренний API оформления по-прежнему требует подтверждённую сессию пользователя. Автоматическое связывание кабинетов ещё не реализовано.

Наборы сейчас могут продаваться только как готовые складские SKU. Если для SKU заведены компоненты, checkout его отклоняет до реализации комплектования; двойного списания нет.

## Локальная проверка

Нужны Node.js 22+ и npm. Все команды выполняются из каталога backend.

```sh
npm ci
npm run build
npm test
```

Тесты поднимают отдельный PostgreSQL на случайном loopback-порту, применяют миграции и останавливают его после выполнения. PostgreSQL не эмулируется. На Windows используется пакет бинарных файлов из embedded-postgres; на других поддерживаемых системах — его штатный запуск. Запуск от root в Linux не поддержан: используйте обычного пользователя. В ограниченном Windows sandbox запуск initdb может потребовать разрешённого выполнения локального процесса вне sandbox.

Данные каждого тестового запуска остаются в `.test-data/<случайный-id>` для диагностики, не попадают в Git или архив результата. Тестовая БД не использует DATABASE_URL. Не запускайте тесты на рабочей БД. Проверка исходного XLSX пропускается, если нет извлечённого source-catalog.json; остальные тесты самодостаточны.

## Импорт исходного каталога

Python-скрипт использует только стандартную библиотеку. XLSX открывается только для чтения.

```sh
python scripts/extract-catalog.py "PATH_TO_SOURCE.xlsx" data/source-catalog.json
npm run import:catalog -- data/source-catalog.json
```

Вторая команда выполняет dry run без подключения к БД. Для применения к выбранной локальной базе:

```sh
npm run migrate
npm run import:catalog -- data/source-catalog.json --apply
```

DATABASE_URL должен быть задан в окружении этих команд. Исходный JSON и полный реестр импорта содержат исходные названия и идентификаторы, поэтому исключены из Git. Контрольная сумма фиксирует файл-источник для повторяемости, но не является криптографической аутентификацией JSON. Импорт запускается только доверенным оператором.

Ожидаемый результат предоставленного файла: 115 строк, 25 товарных черновиков, 90 справочных записей, 49 штрихкодов по всему источнику, 17 кандидатных связей и 6 неоднозначных карточек. Штрихкоды справочных позиций остаются в import_rows, а product_barcodes содержит только коды продукции.

Исходные GUID имеют вариант `...-0a80-...`, не соответствующий строгой проверке RFC UUID. Они проверяются как 128-битная запись GUID и сохраняются отдельно от генерируемых UUID ASAYA. Значения вроде `00001` остаются строками.

Импорт не создаёт цену 0 или остаток 20; таблицы цен и остатков для новых товаров остаются пустыми. Повтор файла не создаёт дублей. Изменение SKU у существующего GUID, конфликт штрихкодов или дубликат идентификатора прерывают всю транзакцию. Повторные выгрузки не перезаписывают утверждённые коммерческие поля и не удаляют отсутствующие товары/штрихкоды.

## Утверждённые соответствия

После первого этапа пользователь утвердил 11 пар карточка–артикул. Они записаны в `data/mapping-approvals.json`; ещё 6 карточек остаются на рассмотрении. Решения по спорным названиям хранятся в `data/catalog-review-decisions.json`. Предположение о новой линейке не считается подтверждением соответствий.

Импорт по-прежнему создаёт неутверждённые связи. После импорта исходного файла выполните отдельный шаг:

```sh
npm run build
npm run approve:mappings
npm run approve:mappings -- --apply
```

Первая команда approve:mappings показывает план без БД. Для --apply нужен DATABASE_URL той локальной базы, куда уже импортирован указанный источник. При использовании .env: `node --env-file=.env dist/scripts/approve-mappings.js --apply`.

Применение проверяет контрольную сумму импортированного источника, исходную строку и текущую пару карточка–артикул. Конфликт отменяет весь пакет. Повторный запуск не дублирует аудит. Цены, остатки, активность и разрешение продаж не меняются. Этот локальный инструмент не имеет публичного HTTP-маршрута; файл согласования редактирует только доверенный оператор. Поле databaseApplied в файле фиксирует состояние рабочей базы на момент записи согласования, а фактический результат конкретного запуска возвращает команда.

В текущей рабочей копии применение проверено на временной тестовой базе. Постоянная рабочая база не подключена.

## Локальная БД и API

При установленном Docker можно использовать `compose.local.yaml`. Это отдельный локальный проект; существующий production compose не изменён. Задайте POSTGRES_PASSWORD и DATABASE_URL с одинаковым новым паролем. Для PostgreSQL 18 том расположен в `/var/lib/postgresql`.

```sh
docker compose -f compose.local.yaml up -d
```

Для запуска API скопируйте `.env.example` в `.env`, замените пароль БД и OTP_SECRET случайными значениями. `.env` не коммитится.

```sh
node --env-file=.env dist/scripts/migrate.js
node --env-file=.env dist/src/server.js
```

По умолчанию API слушает 127.0.0.1:3100. HTTP допускается только локально. Для HTTPS cookie называется `__Host-asaya_session`, для локального HTTP — `asaya_dev_session`.

|---|---|---|
| GET | /health/live | Проверка процесса |
| GET | /health/ready | Проверка доступности БД |
| GET | /api/store/v1/products | Только активные товары с утверждённой ценой и разрешением продажи |
| POST | /api/store/v1/auth/otp/request | Origin; channel и destination |

Пример внутреннего запроса checkout:

SKU и quote из примера являются тестовыми. Без серверной котировки, пользователя и разрешённого товара запрос отклоняется. Поле expectedTotalMinor позволяет сообщить клиенту об изменении суммы; оно не задаёт цену.

## Надёжность и дальнейшее подключение

`recordPaid` — внутренний метод, не HTTP endpoint. Вызывать его сможет только проверенный адаптер провайдера. Неподписанное сообщение и browser success redirect не имеют пути к изменению оплаты. При втором платеже или конфликтующих событиях требуется сверка; метод не пытается автоматически возвращать деньги.

Outbox гарантирует сохранность задачи, но обработчик обязан быть идемпотентным: сбой после внешнего успеха до записи done ведёт к повтору. `processOne` передаёт стабильный idempotencyKey. Lease token не позволяет старому worker перезаписать результат нового. До подключения обработчиков процесс outbox не запускается автоматически и события не помечаются успешно выполненными фиктивно. Для длительных операций потребуется продление lease либо ограниченный timeout адаптера.

Истечение checkout можно выполнять через `node dist/scripts/expire-checkouts.js` при заданном DATABASE_URL. Пакет обрабатывает до 100 заказов за вызов; планировщик должен повторять его. Оплаченные заказы не освобождают резерв по TTL.

Перед production: отдельная роль БД без DDL для приложения, роль мигратора, backup/restore, управление retention для OTP/сессий/PII, staff MFA, ограничения reverse proxy и доверенных proxy-адресов, настройки доставок, политика резервов общего склада, обработка возвратов, версия согласий и сертификация YCP. Текущий trustProxy=false не доверяет X-Forwarded-For; за Caddy лимит по IP будет общим до настройки конкретного доверенного proxy.

Семь миграций применяются одной транзакцией с advisory lock. Автоматических down-миграций с удалением бизнес-данных нет. Возврат приложения на предыдущую версию не должен откатывать сохранённые заказы.

Публичная YCP OpenAPI 0.0.14: https://yandex.ru/support/merchants-ru-ycp/ru/openapi/
Перед следующим этапом уточняются денежные единицы, deprecated query-параметры placed, проверка Bearer токена, повтор checkout и исходящие операции сверки/возврата.
