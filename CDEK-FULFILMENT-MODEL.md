# Схема доставки ASAYA — уточнение владельца 8 сентября 2026

## Уточнение владельца 09.09.2026 — текущая постановка

Последнее подтверждение: после первоначального отказа Максим передал данные доступа, URL YML и подтвердил **MSK2290 / 23401**; скрин показывает магазин ФФ 220216 и интеграцию YML 4273. Владелец затем передал Account/Secure password API СДЭК. Пароли и ключи не повторять в документах, исходниках или выводе. Через этот API успешно выполнены OAuth и GET справочника MSK2290: `fulfillment=true`, адрес и телефон получены. Настройки СДЭК не менялись. YML доступен, но содержит `<offers/>` без товаров. Вход в браузерный ФФ завершился сетевым `Failed to fetch`; после вопроса владельца о необходимости входа продолжили через API и YML.

Подготовлен **отдельный выпуск `20260909-msk2290-v1`** с одним подтверждённым складом и настоящими контактами. Старый пакет двух предварительных складов остаётся приостановленным. Детали и команда: `outputs/ASAYA-MSK2290.md`. Новый выпуск пока не опубликован; серверные тесты и резервная копия обязательны до переключения. Никаких фиктивных остатков. Автоматический импорт ждёт непустой товарной позиции для проверки артикула, численного количества и резервов. Пустая выгрузка не обнуляет базу.

Владелец подтвердил: доставка СДЭК уже подключена внутри Яндекс Чекаута. Товары также хранятся на СДЭК Фулфилменте. Подключение доставки не даёт подтверждения, что backend ASAYA получает сведения о складском хранении и остатках. Нужный дополнительный обмен: **СДЭК Фулфилмент → backend ASAYA → YCP** для складов и доступных остатков.

Расчёт стоимости и сроков, выбор ПВЗ/курьера оставляем подключённой доставке Яндекс ↔ СДЭК. Предыдущая формулировка о необходимости получать варианты доставки в backend ASAYA была ошибочной для этой постановки. Собственный расчёт тарифов, справочник ПВЗ и `/checkout/delivery/options` в этот объём не входят. Настройки работающей доставки не меняем.

Виртуальный склад ASAYA — учётная запись, связанная с подтверждённым складом/складами Фулфилмента. YCP получает описание через `/warehouses`, а доступное количество SKU — в проверке корзины. Откуда Яндекс получает учётные сведения, не определяет физического владельца склада. Не делаем вывода, что Яндекс в принципе не поддерживает фулфилмент. Не агрегируем остатки разных точек в один фиктивный адрес отправления без подтверждённого правила распределения.

Владелец разрешил продолжить работу («погнали делать»). Старый пакет публикации двух предварительных профилей остаётся приостановлен: они не считаются согласованной моделью виртуального склада. Подтверждены документацией Basic auth и использование данных отдельного кабинета ФФ; точные методы складов/остатков, смысл доступного количества/резервов и правила сопоставления SKU ещё требуют проверки. Ключ обычной доставки или пару `client_id/client_secret` не считаем доступом к складским остаткам ФФ.

Для продолжения нужны: фактический доступ Фулфилмента к складам и остаткам, контракт этих методов, подтверждённый ID виртуального склада и его фактические параметры. Тип хранения уже известен: СДЭК Фулфилмент; повторно спрашивать, доставка это или ФФ, не нужно. Владелец подтвердил, что Максим входит отдельно на `seller.ffcdek.ru` по логину и паролю. Подготовлен `outputs/Connect-ASAYA-CDEK-FF.ps1`: скрытый ввод, проверка Basic auth документированным GET справочника индексов и сохранение на Selectel только после принятия данных API. Целевой файл — `/opt/asaya-catalog/secrets/cdek-ff.json`, root, 0600, без перезаписи существующего доступа. JSON сохраняет спецсимволы; он заменяет прежнее предложение `cdek.env`, которое не было реализовано. Данные не передаются в чат, аргументы процессов или репозиторий. Существующий `api.env` не меняется. Скрипт пока не запускался пользователем, файл не подтверждён, синхронизация не включена.

Связь кабинета отправок СДЭК с ФФ ранее подтверждена сообщением Максима. Не создаём второй канал отправки тех же заказов напрямую из ASAYA в ФФ. Прохождение заказа до сборки и согласование локальных резервов с данными ФФ ещё требуют проверки.

Проверка источников 09.09.2026: официальная инструкция https://yandex.ru/support/kit/ru/settings/logistics/integration/sdek описывает подключение службы доставки ключом из `lk.cdek.ru`. Контракт складов/остатков YCP сверён с сохранённой OpenAPI 0.0.14. Сведения о фактическом подключении доставки получены от владельца, а не из входа агента в кабинет. Страницы ФФ, ранее не отдавшие текст веб-инструменту, удалось прочитать в браузере:

- https://help.ffcdek.ru/knowledge/instruction/261821 — REST API использует логин и пароль отдельного кабинета ФФ, Basic auth. Если отдельных данных нет, их выдаёт поддержка; у Максима отдельный вход уже есть. Менять пароль, создавать новый кабинет или требовать ключ доставки не нужно.
- https://help.ffcdek.ru/knowledge/instruction/261823 — пример использует `https://cdek.orderadmin.ru/api/`; GET `delivery-services/postcodes` с фильтром `extId` выбран только для проверки API-входа. Индекс `101000` в проверке не задаёт расположение склада. Авторизованных запросов ещё не было. Подробная ссылка `https://confluence.cdek.ru/pages/viewpage.action?pageId=63359995` не открылась из-за DNS; методы складов/остатков не придумывались.
- https://help.ffcdek.ru/knowledge/instruction/301985 — поддержка ФФ предоставляет актуальные данные интеграции по договору и описанию сценария.
- https://help.ffcdek.ru/knowledge/instruction/300580 и https://help.ffcdek.ru/knowledge/instruction/261826 — Яндекс KIT → СДЭК доставка → ФФ: накладная передаётся на склад для сборки/отгрузки. Это не подтверждение обратной синхронизации остатков в ASAYA. Многоскладовая маршрутизация зависит от города отправителя; инструкция предупреждает о двух складах одного города. Не подменяем реальные точки одной фиктивной и не дублируем заказы.
- https://help.ffcdek.ru/knowledge/instruction/261827 — отдельная выгрузка остатков YML/CML, обновление раз в 30 минут. YML суммирует несколько выбранных складов; для раздельных остатков нужны отдельные выгрузки. CML предусматривает разбивку. Точный контракт количества и резервов здесь не описан; фиды не подключены.

Проверка входа описана в `outputs/ASAYA-CDEK-FF-access.md`. Её успешный маркер не означает подтверждения складских разрешений, импорта остатков или готовности покупок. Локальные проверки с фиктивными данными прошли; требуется запуск владельцем с реальными данными без передачи их в чат.

Дополнительная проверка ссылки владельца `https://ycp42605.checkout.merchants.yandex.ru/settings/ycp`: в доступном браузере кабинет показывает 404, а меню профиля подтверждает отсутствие входа. Настройки кабинета не читались и не менялись. По находящейся на этой странице ссылке «Описание API» открыта публичная инструкция, затем https://yandex.ru/support/merchants-ru-ycp/ru/openapi/ («Принцип работы», версия 0.0.14). Она прямо подтверждает: при создании доставки Яндексом магазин должен отдавать распределение остатков по складам в `/checkout/basket/check`; способы доставки рассчитываются либо Яндексом через API перевозчиков, либо через `/checkout/delivery/options` магазина — в зависимости от выбранной настройки. `/checkout` повторно проверяет цены и резервирует товар, затем следуют `/checkout/cancel` или `/checkout/placed`. Ответ магазина — до 5 секунд; входящие запросы авторизуются Bearer-токеном. Для уже подключённой владельцем доставки сохраняем первый вариант. Способ чтения остатков Фулфилмента СДЭК эта инструкция не устанавливает.

Ниже — историческая постановка от 08.09.2026, которую нельзя использовать как разрешение публикации или окончательную схему интеграции.

Товары хранит, комплектует и отправляет СДЭК. Выбор фактической точки отправления относится к работе СДЭК. Служба доставки подключается в кабинете Яндекс Чекаута; отдельную прямую интеграцию сайта с СДЭК без необходимости не строим. Доставка планируется по России, доступные варианты и сроки должны определяться сервисом при оформлении.

Москва — предварительный город первой поставки. Это не подтверждённый адрес или идентификатор склада, не факт наличия товара и не ограничение доставки Москвой. Екатеринбург, Новосибирск, Краснодар, Казань, Санкт-Петербург и, возможно, Хабаровск — отдалённые планы по мере роста продаж. Эти точки не создавались в БД и не передавались Яндексу как действующие.

Исправлена преждевременная формулировка админки «нужно настроить склад отправки». Количество внутренних складов убрано из пользовательской проверки карточек. При отсутствии доступного остатка показано, что он пока не подтверждён в системе. Это не требование вручную вести склады и не утверждение о нулевом физическом остатке в СДЭК. Проверки остатков и резервов в бэкэнде сохранены: схема фулфилмента не даёт права продавать неизвестный остаток как доступный. Карточки, цены, фотографии и данные пользователей не менялись.

Что подтверждено документацией:

- Инструкция YCP отдельно описывает подключение службы доставки и импорт/настройку точек отправления: https://yandex.ru/support/merchants/ru/buy-button .
- Сохранённая OpenAPI 0.0.14 требует /warehouses, когда чекаут получает варианты от службы доставки напрямую: точка отправления нужна расчёту. В /checkout/basket/check при управлении доставкой Яндексом передаются остатки по таким точкам. Собственный /checkout/delivery/options нужен при самостоятельном управлении доставкой, его для выбранной схемы не добавляем.
- Инструкция подключения СДЭК в Яндекс KIT описывает авторизацию интеграционным ключом из кабинета СДЭК: https://yandex.ru/support/kit/ru/settings/logistics/integration/sdek . Она описывает службу доставки, но не подтверждает автоматическое распределение заказов между фулфилмент-складами СДЭК, импорт всех их остатков или передачу заказов на сборку. Экран в конкретном кабинете может отличаться; логин/ключ сам по себе не считается доказательством этих возможностей.
