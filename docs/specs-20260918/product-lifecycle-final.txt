ASAYA — ФИНАЛЬНОЕ СИСТЕМНОЕ ТЗLIFECYCLE ТОВАРА
Draft → Published → Unpublished → Deleted
18 сентября 2026
Цель. Зафиксировать единую и окончательную модель жизненного цикла товарной карточки в Admin, backend и storefront. После внедрения этой логики к вопросу публикации/видимости товара не возвращаемся.

Главное правило. Товар виден на сайте потому, что он Published. Товар можно купить потому, что он Published И доступен по stock. Publication и stock — независимые состояния.

2. Draft — создание новой карточки
Новая карточка после действия «Создать новый товар» создаётся в статусе Draft.
2.1. Минимальные обязательные поля
Название товара.
Цена.
Состав товара.
Описание товара.
Минимум одна фотография.
2.2. Правило публикации
Пока хотя бы одно обязательное поле не заполнено, кнопка «Опубликовать товар» disabled.
Когда все обязательные поля заполнены, кнопка становится активной.
После нажатия товар получает Published и появляется на storefront.
Stock не является обязательным полем публикации. Даже stock = 0 не блокирует сам факт публикации.
Не добавлять новые обязательные поля без отдельного бизнес-решения владельца.
3. Published — опубликованный товар
Неизменяемый принцип. Если товар уже Published, он остаётся Published до явного действия администратора «Снять с публикации». Миграции, stock sync, stock=0 и технические обновления не имеют права автоматически переводить товар в Draft/Unpublished.

Published товар отображается на главной, в витринах, категориях, подборках, поиске и на PDP.
При stock > 0 товар доступен к покупке.
При stock = 0 товар остаётся видимым; показывается «Нет в наличии»; добавить/купить нельзя.
При восстановлении stock товар автоматически снова становится purchasable без повторной публикации.
Published/visible flag не должен вычисляться из stock.
4. Редактирование Published товара
Редактирование само по себе не снимает товар с публикации.
Если обязательные поля остаются валидными, товар после сохранения остаётся Published.
Если администратор пытается удалить обязательное поле у Published товара, сохранение блокируется с понятным сообщением, какое поле обязательно.
Запрещено поведение «удалили обязательное поле → система молча сняла товар с публикации».
Чтобы намеренно сделать товар невидимым, используется только отдельное действие «Снять с публикации».
5. Unpublished — снятие с публикации
В карточке Published товара в Admin есть кнопка «Снять с публикации».
После действия товар исчезает со storefront, но карточка и все данные остаются в Admin.
Цена, описание, состав, фото, SKU и stock не удаляются и не обнуляются.
Для Unpublished товара доступно действие «Опубликовать товар».
Повторная публикация разрешена только если минимальные обязательные поля заполнены.
6. Deleted — удаление
Внизу карточки есть действие «Удалить товар».
Удаление требует отдельного подтверждения.
Если товар никогда не участвовал в заказах и не имеет исторических связей, допускается физическое удаление.
Если товар участвовал в заказах/истории, удаление не должно ломать order history: допустим soft-delete/archive, даже если UI для администратора называется «Удалить товар».
Deleted/archived товар не показывается на storefront и не может участвовать в новых заказах.
7. Корзина и отсутствие остатка
Если Published товар уже был добавлен в корзину и затем stock стал 0, позиция не удаляется бесследно.
Она остаётся в UI приглушённой и получает «Нет в наличии».
Позиция исключается из purchasable subtotal/total и не передаётся в Yandex Checkout.
Увеличение количества недоступного товара запрещено.
Если все позиции недоступны, checkout disabled.
Если stock восстановился, позиция автоматически снова становится активной.
8. Миграция существующего production-каталога
Критично для текущего релиза. Товары, которые уже отображаются на действующем production-сайте, являются уже Published. Перенос в canonical DB/новую Admin не должен сбрасывать их в Draft или Unpublished.

1. Сопоставить production товары и canonical DB по SKU.
2. Для уже опубликованных production товаров сохранить/восстановить Published.
3. Не менять существующие цены, контент, фото и иные коммерческие данные в рамках этой задачи.
4. Не создавать дубликаты карточек вместо существующих.
5. Если у конкретного товара реально отсутствует обязательное поле, зафиксировать именно этот единичный конфликт; не считать весь каталог неопубликованным.
6. Stock=0 не является причиной сбросить Published.

10. Запрещённые зависимости
Нельзя скрывать Published товар из-за stock=0.
Нельзя автоматически снимать Published из-за миграции или stock sync.
Нельзя использовать stock > 0 как фильтр storefront visibility.
Нельзя превращать все существующие товары в Draft при переходе на новую DB/Admin.
Нельзя менять publication state по цене/остатку/количеству заказов без явного действия администратора.
Нельзя молча снимать Published при невалидном редактировании — такое сохранение должно блокироваться.

12. Что Codex должен сделать
1. Проверить текущую реализацию lifecycle и привести её к этой state model.
2. Реализовать/проверить disabled Publish для Draft без обязательных полей.
3. Реализовать/проверить явные действия Publish и Unpublish в Admin.
4. Заблокировать сохранение Published карточки без обязательного поля.
5. Сохранить Published state существующего production-каталога при переходе на canonical DB.
6. Проверить storefront и cart behavior при stock=0.
7. Прогнать acceptance tests раздела 11.
8. Commit + push только связанных изменений; unrelated UI/архитектуру не трогать.
9. В отчёте указать: какие товары были ошибочно unpublished, что исправлено, и подтверждение, что production lifecycle соответствует этому ТЗ.
Финальная формула. VISIBLE = Published. PURCHASABLE = Published AND stock > 0. Draft, Unpublished и Deleted на storefront не отображаются. Это окончательное системное правило ASAYA.
