Назначение. Этот пакет заменяет один большой документ для следующих backend-задач. Каждый файл — одна узкая техническая цель. Codex получает только текущий файл + этот индекс при необходимости.

1. Подтверждённая схема после совместного звонка ASAYA + Yandex + CDEK
На сайте ASAYA пользователь нажимает «Оформить заказ» и переходит в Yandex Checkout по YCP-интеграции.
При запуске checkout ASAYA передаёт данные заказа/корзины, включая внутренний номер заказа, товары и количество. Складские остатки в этот момент отдельно не передаются.
Находясь в Yandex Checkout, YCP вызывает API ASAYA для проверки корзины и запрашивает актуальные цены/доступность/количество через checkout/basket/check.
ASAYA заранее регулярно получает фактические остатки из CDEK/CDEK Fulfillment и отвечает YCP из единого локального stock-layer/cache.
После успешного оформления Yandex самостоятельно создаёт доставку/отправление в CDEK. ASAYA не вызывает POST /v2/orders для создания второй накладной.
По устному подтверждению CDEK на совместном звонке Yandex передаёт в CDEK внутренний номер заказа ASAYA; он должен быть виден в накладной/client order number. Это требуется окончательно подтвердить реальным E2E-заказом.
После создания отправления ASAYA получает/актуализирует статусы через уже подготовленный CDEK webhook + GET fallback и связывает shipment с внутренним заказом по подтверждённому identifier.
Финальное доказательство всей цепочки — один реальный минимальный заказ.
2. Что закрыто и больше не обсуждается
Вопрос
Решение
Кто создаёт CDEK shipment?
Yandex. ASAYA shipment/waybill не создаёт.
Нужно ли ASAYA передавать заказ в CDEK Fulfillment?
Нет.
Как YCP получает остатки?
От API ASAYA при checkout/basket/check.
Откуда ASAYA берёт остатки?
Из фактического CDEK/CDEK Fulfillment stock source, синхронизированного заранее.
Должны ли остатки быть видимы владельцу?
Да: Admin → Аналитика → Остатки.
Можно ли матчить shipment по телефону/ФИО/времени?
Нет.
Correlation Yandex→CDEK
Ожидаемый ключ — внутренний номер заказа ASAYA, который Yandex передаёт CDEK; live E2E должен подтвердить точное поле/формат.
Можно ли создавать второй механизм stock только для YCP?
Нет. Admin и YCP используют один stock-layer.
Скрывать ли товар при stock=0?
Нет. Все опубликованные товары видимы; stock влияет только на возможность покупки.
Что происходит с PDP при stock=0?
PDP остаётся доступной; показывается «Нет в наличии», добавление в корзину запрещено.

Правила для Codex
Работать только в области этого файла: текущий выбранный файл из пакета. Не выполнять следующие ТЗ автоматически.
Не переосмысливать закрытые бизнес- и архитектурные решения. Если решение уже указано как закрытое, его нужно реализовать, а не предлагать альтернативу.
Если точный ответ есть в официальной документации, сначала использовать документацию. Не задавать владельцу вопрос, на который документация уже отвечает.
Не придумывать endpoint/field/identifier/status/формат провайдера.
Не делать unrelated refactor и не менять замороженные части.
После реализации: tests/build → commit → push → отчёт LOCAL/GITHUB/PRODUCTION → STOP.
Production — только по отдельному разрешению.
