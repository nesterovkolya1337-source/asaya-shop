## Implementation

- Required session/order/payment fields still validate strictly; body/query contradictions reject. Bearer authentication precedes parsing; account and environment scope remain enforced.
- Online placement is accepted without acquiring ID. `ycp_sessions.acquiring_id` remains NULL when absent; the local payment ledger uses `placement:<YCP order ID>` as an internal unique reference, never as a fabricated acquiring transaction ID. Supplied acquiring IDs remain verbatim and cannot bind two orders.
- `online_payment_method` now persists in the YCP session instead of being discarded.
- Session/order locks, unique external order identifiers and placement hash ensure one finalized order, payment, profile association and paid event under concurrent identical replays. Changed replays conflict instead of silently changing money or metadata. A replay that adds previously omitted payment metadata is also a changed payload and requires reconciliation; no undocumented enrichment contract was assumed.
- Profile upsert uses the normalized phone. Existing nonempty customer-edited name/email remain unchanged; only empty fields are filled from received checkout data. Contact association does not create authentication or grant order access. Existing SMS claim rules remain in place.
- All placement/order/payment/profile/history/outbox changes are one database transaction. A profile or audit write failure returns an error and rolls back the entire placement, including payment and dedupe markers, allowing a clean retry.
- A confirmed online payment received after cancellation is saved as paid and retained for manual review. Cancellation/released stock remain unchanged; no normal paid-order dispatch event is emitted. Repeated late messages do not duplicate payment/history.
- Logs contain server request ID, route, result and internal order/hash correlation only. Tests exclude phone, name, email, address, token, raw session and acquiring identifiers.

## Yandex owns CDEK; CloudKassir stays fiscal

The obsolete `FULFILLMENT_ENABLED=true` configuration now fails startup even with valid credentials. `buildApp` independently rejects injected fulfillment dispatch wiring. This prevents an old order.paid consumer from creating an ASAYA→Fulfillment order alongside Yandex. Legacy implementation files remain for historical isolated tests; they are not a supported production integration path. Stock synchronization is independent and unaffected.

No CloudKassir configuration, API call, receipt owner or receipt trigger was changed. CloudKassir is not used as payment truth. No second fiscal receipt is generated by this task. Actual receipt issuance can only be confirmed during the approved real E2E (Tasks 13/14), and is not claimed as locally verified.

## Migration 025 — prepared, not applied to production

`backend/migrations/025_ycp_payment_method.sql` adds one nullable checked text column to `ycp_sessions`. Existing rows remain NULL; their payment method cannot be reconstructed from a hash and is not guessed. No backfill, record deletion or existing-data rewrite.

The migration was applied only by the isolated temporary test harness. Production application needs the separate migration approval/backup in the deployment plan, alongside other approved pending migrations. Run it before the new backend, which writes this column. Operational rollback is to the previous code while retaining the nullable column; do not drop data as an automatic rollback.
