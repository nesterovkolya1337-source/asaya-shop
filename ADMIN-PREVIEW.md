# Админка каталога ASAYA — локальный этап

Администратор может создавать новые товары и исправлять существующие через сервер. Неутверждённый ассортимент больше не блокирует разработку: данные можно уточнить и опубликовать позже. Витрина принимает новые карточки из базы, включая новые адреса товаров и инструкций, без изменения исходного списка и без пересборки.

## Готовые возможности

- Отдельный вход сотрудника: почта, пароль, шестизначный код приложения-аутентификатора. Покупательские cookie не дают административных прав.
- Поиск товаров и просмотр списка порциями по 50 записей.
- Новый товар, черновик, сохранение, публикация и скрытие с витрины.
- Редактируются название, категория, тип товара/комбо/подарочный набор, описание, объём, особенности, применение, состав, аромат, основное фото и галерея с загрузкой файлов или по ссылкам, обычная и конечная цена, метка, инструкция, предостережения, рекомендации, оценки свойств, вес и размеры.
- Импортированные карточки можно редактировать без повторного изменения исходного XLSX. Известные поля витрины предлагаются в форме как заготовка; администратор проверяет их перед сохранением и публикацией. Тип спорного набора автоматически не утверждается.
- Сохранение черновика не меняет опубликованные данные. Публикация отдельная: проверяются обязательные поля, цены, уникальность адреса и тип набора.
- Скрытие убирает товар из публичного каталога, но сохраняет его запись, черновик, заказы и историю. Скрытый товар в уже существующей корзине блокирует оформление.
- Остаток по существующим складам корректируется отдельно, сразу. Нельзя уменьшить его ниже резерва; изменение устаревшего значения отклоняется.
- Версии черновиков защищают от перезаписи правок другого сотрудника. При конфликте нужно загрузить карточку с сервера и сверить изменения.
- Журнал содержит действие, время и идентификатор сотрудника. Фиксируются сохранения, публикации, скрытия и корректировки остатка.
- Старые заказы сохраняют прежние названия, цены и суммы независимо от дальнейшего редактирования товара.

## Границы этой версии

Это рабочий локальный этап каталога, не завершённый кабинет всего магазина и не production-запуск.

Загрузка фотографий с компьютера и хранение в базе добавлены; подробности в MEDIA-PREVIEW.md. Ссылки HTTPS и существующие пути /images/… также поддерживаются. Общая медиатека и проверка доступности внешних изображений ещё не добавлены. Наборы учитываются как отдельные заранее собранные товары со своим остатком; редактор компонентного состава и автоматический расчёт складских остатков из компонентов ещё не реализованы.

Артикул сохранённой записи и адрес уже опубликованной карточки защищены от изменения. Для другого артикула создаётся другой товар. Перенос внешних идентификаторов, штрихкодов и переименование опубликованных адресов с перенаправлениями — отдельные операции будущего этапа.

На этом этапе нет управления сотрудниками через веб, восстановления второго фактора, редактора складов, полного процесса обработки заказов и возвратов, промокодов и аналитики. Система использует роль admin; разделение прав менеджеров ещё не подключено. SEO-заголовки серверных страниц пока общие, хотя название и содержимое карточки берутся из опубликованных данных.

Вход покупателей, реальная оплата, СДЭК и интеграция YCP остаются отдельными задачами. Спорные названия и ассортимент — вопросы наполнения, их можно решить в админке.

## Изолированный просмотр

Архив ASAYA-backend-photos.zip — накопительное дополнение к отдельной копии исходного проекта на fa2164a. Включает предыдущие этапы. Изображения исходного сайта, установленные зависимости, реальные базы, исходный XLSX и секреты в архив не входят.

Нужен Node.js 22.6+ (проверено на 24.19). В первом PowerShell, из backend:

```powershell
npm ci
$env:ASAYA_PREVIEW_ADMIN='enabled'
$env:ASAYA_PREVIEW_DELIVERY='enabled'
npm run preview:checkout
```

Скрипт создаёт отдельную временную PostgreSQL, не читает DATABASE_URL и не импортирует реальные товары. Он создаёт случайный тестовый пароль для admin-preview@example.test и печатает тестовые коды второго фактора в терминале. Это разрешено только внутри данного изолированного стенда; в штатном сервере коды администратора не печатаются.

Во втором PowerShell, из корня копии проекта:

```powershell
npm ci
$env:NEXT_PUBLIC_CATALOG_SOURCE='backend'
$env:NEXT_PUBLIC_TEST_CHECKOUT='true'
$env:ASAYA_BACKEND_ORIGIN='http://127.0.0.1:3100'
npm run dev -- --hostname 127.0.0.1 --port 3200
```

Откройте http://127.0.0.1:3200/admin/. Введите тестовую почту, выведенный пароль и последний код из терминала. Никаких внешних писем, SMS, платежей и отправок нет.

Проверочный путь: добавить товар → заполнить данные → сохранить черновик → указать остаток → опубликовать → открыть витрину и карточку → скрыть товар. Тестовые фото можно взять из существующих /images/figma/page2-packshots/. Значения цен и остатков стенда вымышленные.

Стенд автоматически останавливается через 15 минут; Ctrl+C завершает раньше. Каждый запуск создаёт новую базу и новый пароль. Кластеры остаются в игнорируемом backend/.test-data для диагностики.

## Подключение к постоянной локальной базе

1. Примените все миграции, включая 008_staff_catalog.sql и 009_product_media.sql, обычной командой npm run migrate.
2. Задайте отдельный случайный STAFF_SECRET длиной не менее 32 символов в backend/.env. Без него все административные маршруты закрыты.
3. Подготовьте приватный JSON-файл вне проекта с полями email, password, totpSecret. Пароль — не менее 14 символов. totpSecret — уникальный случайный Base32-ключ из A–Z и 2–7, не менее 32 символов, заранее добавленный в приложение-аутентификатор сотрудника. Настройки: SHA-1, 6 цифр, 30 секунд. Не используйте ключи или пароли из примеров/тестов.
4. Из backend выполните npm run build, затем npm run create:admin -- C:/private/asaya-admin.json. Скрипт выводит только идентификатор созданного сотрудника; публичного маршрута выдачи административного доступа нет.
5. После передачи ключа сотруднику храните или удалите приватный файл по принятому порядку управления секретами. Не добавляйте его в репозиторий или архив.
6. Запустите штатный backend и серверную витрину. PUBLIC_ORIGIN должен совпадать с адресом витрины. Для доступа к админке флаг тестового оформления не нужен.

STAFF_SECRET защищает сессии и зашифрованные ключи второго фактора. Его нельзя просто заменить без подготовки повторной привязки аутентификаторов. Самостоятельное восстановление пароля/второго фактора в веб-интерфейсе пока отсутствует. Штатный сервер по-прежнему запрещает NODE_ENV=production.

## Безопасность и технические опоры

Пароли хранятся как scrypt с отдельной случайной солью, ключи аутентификаторов — с AES-256-GCM. Административная сессия длится час, хранится в отдельной HttpOnly/SameSite cookie; в базе хранится хеш токена. Проверяются Origin и CSRF, роль и блокировка сотрудника. Повтор уже принятого временного кода запрещён, ограничения попыток по адресу и IP сохраняются в базе.

Реализация TOTP сверена с [RFC 6238](https://www.rfc-editor.org/rfc/rfc6238), в том числе по контрольным векторам. Для парольного хеширования используется [Node.js crypto.scrypt](https://nodejs.org/api/crypto.html#cryptoscryptpassword-salt-keylen-options-callback).

Новые API находятся под /api/admin/v1: media, auth/login, auth/me, auth/logout, products, products/:id, products/:id/publish, products/:id/unpublish, products/:id/stock, products/:id/history. Прокси Next.js ограничен локальным backend.
