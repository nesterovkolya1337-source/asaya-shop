# ASAYA: связь запросов YCP с заказами в журнале

Сервер генерирует UUID для каждого запроса и возвращает его в X-Request-ID. Значение входящего X-Request-ID игнорируется. В существующих ответах об ошибках поле requestId использует этот же номер; JSON контрактов YCP не расширяется.

При включённом штатном журнале запись завершения запроса содержит номер, метод, шаблон маршрута, HTTP статус, длительность ответа и безопасную категорию ошибки. Для авторизованных запросов YCP с session_id или order_id выполняется поиск в текущем кабинете и окружении. Если соответствие найдено, добавляется внутренний orderId ASAYA. По нему можно сопоставить запросы, запись заказа и aggregate_id событий очереди из раздела «Проверка интеграции».

Исходные идентификаторы из запроса не выводятся: даже в них может находиться произвольный текст. Вместо них журнал содержит стабильную HMAC-метку ycpReference с типом session/order. Метка учитывает кабинет и окружение. Запросы к одной неизвестной сессии можно сопоставить между собой до создания заказа. Метки сессии и внешнего заказа различны; после появления заказа их объединяет orderId.

Возможные результаты поиска: matched — найден заказ; unmatched — совпадения нет; unavailable — поиск недоступен. Неавторизованные запросы не запускают поиск и не получают метку или orderId в журнале. Тело запроса, query string, контактные данные, токены и исходные сообщения исключений не записываются. Для внутренних исключений выводится только INTERNAL_ERROR, без произвольного error.code.

Поиск выполняется после отправки ответа и не меняет бизнес-транзакцию. Длительность фиксируется до диагностического поиска. Сбой поиска сохраняется как unavailable и не отменяет успешную операцию. При logger=false поиск не выполняется. HMAC использует серверный OTP_SECRET; его смена изменит метки, но UUID запроса и заказа сохранятся в ранее записанных строках.

## Как искать проблему

1. Получить X-Request-ID из ответа API или requestId из ответа об ошибке.
2. Найти соответствующую строку серверного журнала.
3. Если есть orderId, найти заказ и его события. Если заказа нет, искать повторные обращения по ycpReference.
4. Проверить HTTP статус, категорию ошибки и состояние заказа. Ошибка диагностики не равна ошибке оплаты.

Это структурированные записи в штатном серверном журнале. Централизованное хранение, срок хранения и ротация журналов на боевом сервере ещё не настроены. Отдельный поиск запросов внутри админки не добавлен. Новых миграций и внешних отправок нет; исходный проект не изменён.
