# Серверный вход ASAYA — локальный этап

В режиме `NEXT_PUBLIC_CATALOG_SOURCE=backend` личный кабинет подключён к серверному входу. Добавлены выбор email/SMS, запрос одноразового кода, проверка шести цифр, повторная отправка с таймером, смена контакта, восстановление сессии и выход.

Архив этого этапа содержит полный backend и все изменения витрины относительно исходной версии `fa2164a`. Это дополнение к отдельной копии исходного проекта, а не полный проект с изображениями. При переносе в более новую версию сравните файлы перед заменой.

## Что работает

- Код считается отправленным только после успешного ответа сервера. Отказ провайдера, неверный или истёкший код, лимит попыток и отсутствие сети отображаются отдельно.
- После успешного входа сервер устанавливает HttpOnly cookie на 7 дней. Клиент не сохраняет ключ сессии, код или защитный токен в localStorage.
- GET `/api/store/v1/auth/me` проверяет действительность сессии и возвращает id, роль customer и CSRF-токен. CSRF вычисляется через HMAC от ключа сессии с отдельным префиксом; в БД остаётся только его хеш. Токен стабилен для сессии, поэтому обновление страницы и другая вкладка не ломают выход.
- После загрузки страницы и возвращения фокуса кабинет проверяет сессию на сервере. Ошибка сети не подменяется успешным входом. Повторную проверку можно запустить вручную.
- Выход отправляет серверный запрос с CSRF, отзывает сессию и очищает cookie. Ошибка выхода не показывает ложный успех.
- Старые локальные email-профили из деморежима не становятся серверными аккаунтами. Покупки и отзывы в этом режиме ещё не подключены. История и отмена заказов описаны в `ORDERS-PREVIEW.md`.

Клиентские таймеры помогают пользователю, а реальные сроки действия и лимиты всегда проверяет backend. При потере ответа после проверки кода кнопка «Проверить состояние входа» позволяет проверить, успел ли сервер установить cookie.

## Как запускать

Используйте `CATALOG-PREVIEW.md` для подготовки проекта. В backend/.env задайте `PUBLIC_ORIGIN=http://127.0.0.1:3200`, `COOKIE_SECURE=false` для локального HTTP, адрес своей локальной БД и случайный OTP_SECRET. Origin должен точно совпадать с адресом витрины, включая порт; localhost и 127.0.0.1 считаются разными адресами.

После сборки backend запустите `node --env-file=.env dist/src/server.js` из backend. В другом PowerShell, из корня рабочей копии:

```powershell
$env:NEXT_PUBLIC_CATALOG_SOURCE='backend'
$env:ASAYA_BACKEND_ORIGIN='http://127.0.0.1:3100'
npm run dev -- --hostname 127.0.0.1 --port 3200
```

Откройте `http://127.0.0.1:3200/account/`. Локальный прокси пропускает каталог, четыре маршрута входа (me, otp/request, otp/verify, logout), список, подробности и отмену заказов. Создание заказов и оплата через него пока не подключены.

Обычный запуск по-прежнему использует DisabledOtpSender. Поэтому без адаптера email/SMS он вернёт «Отправка кодов пока недоступна»; реальных писем и SMS не будет. Для подключения поставщика реализуется существующий OtpSender и передаётся в buildApp. Тестовый отправитель не включён в сервер запуска и не является способом входа для покупателей.

Ранее созданные временные сессии со случайным невосстановимым CSRF-токеном требуют повторного входа после этого обновления. Миграции схемы не нужны. Production-запуск backend по-прежнему запрещён.

## Проверка

- 21 тест backend на реальном временном PostgreSQL: в том числе восстановление CSRF после входа, изоляция токенов разных сессий, отзыв при выходе и истечение срока.
- 8 клиентских тестов: каталог и запросы авторизации; `npm run test:client`.
- Проверки TypeScript, ESLint, сборка режима backend и прежний статический export прошли.
- В браузере проверены недоступный отправитель, тестовая отправка, неверный код, успешный вход, восстановление после перезагрузки и выход. Использованы только вымышленные контакты и локальный тестовый отправитель; внешних отправок не было.

Следующий шаг для настоящего входа покупателей — выбрать и подключить почтового/SMS-провайдера. Оплата, доставка и разрешение продажи товаров этим этапом не включаются.
